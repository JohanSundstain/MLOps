# Инференс и анализ площади

Документ описывает, как применить обученную модель к новым снимкам: формат входа, внутренний
конвейер, расчёт площади и её изменения, отчёты и варианты сервинга.

## 1. Входные данные

Один GeoTIFF на дату:

| Требование  | Значение                                                                       |
| ----------- | ------------------------------------------------------------------------------ |
| Каналы      | ровно **4**, порядок **B2, B3, B4, B8** (blue, green, red, NIR)                |
| Разрешение  | 10 м (проверяется неявно через transform)                                      |
| Значения    | `uint16` reflectance (масштаб 10 000) **или** `float32` reflectance в `[0, 1]` |
| Геопривязка | обязательна: CRS + geotransform                                                |
| Пара дат    | одинаковая сетка: CRS, размер и transform должны совпадать                     |

Для сравнения двух дат проверка жёсткая (`inference/raster.py::assert_comparable`): при
разных CRS/размерах/сдвиге выдаётся понятная ошибка — «перепроецируйте/обрежьте», потому что
сравнивать площади на разных сетках нельзя.

Пример данных можно сгенерировать из тех же сцен, на которых учились:

```bash
python commands.py make-example            # data/example/chany_2023-07-15.tif и ..._2024-07-20.tif
```

## 2. Запуск

```bash
# одна дата — только площадь
python commands.py infer --image-a data/example/chany_2023-07-15.tif

# две даты — площадь, абсолютное и относительное изменение
python commands.py infer \
    --image-a data/example/chany_2023-07-15.tif \
    --image-b data/example/chany_2024-07-20.tif \
    --date-a 2023-07-15 --date-b 2024-07-20
```

Полезные параметры (через `--overrides`):

| Параметр                   | Смысл                                     | Пример                              |
| -------------------------- | ----------------------------------------- | ----------------------------------- |
| `infer.backend`            | `onnx` (по умолчанию) или `torch`         | `infer.backend=torch`               |
| `infer.tile_overlap`       | перекрытие тайлов в пикселях (усреднение) | `infer.tile_overlap=32`             |
| `infer.batch_size`         | тайлов на батч                            | `infer.batch_size=16`               |
| `infer.roi`                | bbox в EPSG:4326 для ограничения области  | `infer.roi=[77.4,54.85,77.6,54.95]` |
| `infer.save_probabilities` | сохранить карту вероятностей              | `infer.save_probabilities=true`     |
| `infer.threshold`          | переопределить порог из bundle            | `infer.threshold=0.6`               |

## 3. Внутренний конвейер

```
GeoTIFF (4 канала, uint16)
   │  read_raster: деление на 10000, если целые
   ▼
float32 reflectance
   │  clip(0, 0.4) → (x − mean_train) / std_train   (статистики из bundle.json)
   ▼
нормированный тензор (4, H, W)
   │  iter_tiles: тайлы 256×256, шаг 256 − overlap
   │  extract_tile: паддинг снизу/справа (reflect) до 256
   ▼
батчи (N, 4, 256, 256)
   │  backend: onnxruntime или PyTorch
   ▼
вероятности (N, 1, 256, 256)
   │  stitch_probabilities: обрезка паддинга, усреднение в перекрытиях
   ▼
карта вероятностей (H, W)
   │  threshold из bundle.json (0.55)
   ▼
бинарная маска (H, W) → площадь, отчёт
```

Ключевые детали:

- **Паддинг** только снизу и справа: валидная часть тайла всегда начинается в `[0, 0]`, поэтому
  склейка — это просто нарезка `[:h, :w]`;
- **Перекрытия** (если `tile_overlap > 0`) усредняются: аккумулятор делится на счётчик попаданий;
- **Нормализация берётся из bundle**, а не пересчитывается по входному снимку: иначе статистики
  зависели бы от того, что модель видит в момент предсказания;
- **Сигмоида внутри ONNX-графа**: наружу отдаются вероятности, клиенту не нужно знать про логиты.

## 4. Площадь воды

`geo.py`. Площадь нельзя считать как «число пикселей × 100 м²» без оговорок: у растров в
географической проекции (EPSG:4326) пиксель на разных широтах покрывает разную площадь.

- **Проекционная CRS (UTM)** — площадь пикселя постоянна:
  `area = |a·e − b·d|` (детерминант матрицы преобразования), `S = N_pixels × area`;
- **Географическая CRS** — площадь считается по строкам: для каждой строки строится пиксельный
  прямоугольник в градусах и его площадь вычисляется геодезически на эллипсоиде WGS84
  (`pyproj.Geod.polygon_area_perimeter`), затем суммируется с учётом числа водных пикселей в
  строке. Повёрнутые растры в географической CRS не поддерживаются (нужна перепроекция).

Для Sentinel-2 в UTM (наш случай) работает первая формула: пиксель 10 м × 10 м = 100 м².

## 5. Изменение площади

```
ΔS = ((S₂ − S₁) / S₁) × 100 %
```

- `S₁ = 0` → относительное изменение **не вычисляется**: в JSON пишется `"delta_percent": null`,
  в консоли — «relative change not defined (S1 = 0)». Это требование постановки задачи;
- абсолютное изменение считается всегда: `delta_m2`, `delta_km2`.

## 6. Что получается на выходе

```
predictions/
├── <имя A>_mask.tif            маска воды uint8 0/1, с CRS и transform
├── <имя B>_mask.tif            то же для второй даты
├── <имя>_probabilities.tif     float32 (если infer.save_probabilities=true)
├── water_report.json           площади, дельта, параметры модели, пути к артефактам
└── water_report.png            по строке на дату: RGB | маска | overlay
```

Фрагмент `water_report.json`:

```json
{
  "first": {
    "date": "2023-07-15",
    "crs": "EPSG:32643",
    "pixel_size_m": [10.0, 10.0],
    "water_pixels": 962085,
    "area_m2": 96208500.0,
    "area_km2": 96.2085
  },
  "second": { "date": "2024-07-20", "area_km2": 96.7942, "water_fraction": 0.923 },
  "change": { "delta_m2": 585700.0, "delta_km2": 0.5857, "delta_percent": 0.6088 },
  "model": { "backend": "onnx", "threshold": 0.55, "band_order": ["blue", "green", "red", "nir"] }
}
```

Отчёт самодостаточен: по нему видно, какой моделью, с каким порогом и на какой сетке получены
числа, поэтому его можно прикладывать к результатам мониторинга.

## 7. Бэкенды инференса

| Бэкенд                | Что нужно                                | Когда использовать                                         |
| --------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| `onnx` (по умолчанию) | `weights/lake_unet.onnx` + `bundle.json` | быстрее, не требует PyTorch-модели, так работает продакшен |
| `torch`               | `weights/lake_unet.ckpt` + `bundle.json` | отладка, сравнение с обучением                             |

Оба дают одинаковый результат (расхождение проверено при экспорте: `2,68e-07`), потому что
ONNX-граф — это та же сеть с сигмоидой внутри.

## 8. Экспорт в ONNX

```bash
python commands.py export-onnx
```

Что делает `export/onnx.py`:

1. читает `bundle.json`, собирает сеть и загружает `state_dict`;
2. оборачивает в `ProbabilityModel` (сигмоида внутри графа), переводит в `eval`;
3. экспортирует с `opset 17`, именами `image` → `probabilities`, динамическими осями batch
   (и height/width, если `export.dynamic_spatial=true`);
4. проверяет `onnx.checker`, затем сравнивает выход с PyTorch через `onnxruntime`
   (допуск `export.atol = 5e-4`, фактическое расхождение ~3e-7);
5. записывает в метаданные ONNX порог, порядок каналов, масштаб reflectance и git commit.

Проверить артефакт без запуска модели:

```bash
python commands.py export-onnx        # печатает inputs/outputs/opset/размер
```

## 9. TensorRT

```bash
python commands.py export-tensorrt --dry-run   # напечатать команду
python commands.py export-tensorrt             # собрать движок (GPU NVIDIA + trtexec)
scripts/build_tensorrt.sh                      # то же из shell
```

Сборка идёт из ONNX через `trtexec` с `--fp16` и фиксированной формой `image:1x4x256x256`.
Без TensorRT команда печатает инструкцию с запуском контейнера
`nvcr.io/nvidia/tensorrt:24.08-py3`. Результат — `weights/lake_unet.engine`, который
используется внешним рантаймом (в самом проекте инференс на TensorRT не реализован, потому что
движок привязан к конкретному GPU и версии TensorRT).

## 10. Inference server

### 10.1. MLflow Serving

```bash
python commands.py serve-mlflow
# печатает model URI и создаёт weights/request.json
mlflow models serve -m runs:/<run-id>/model --host 127.0.0.1 --port 5001 --env-manager local
curl -X POST http://127.0.0.1:5001/invocations \
     -H 'Content-Type: application/json' -d @weights/request.json
```

Модель логируется как ONNX-модель MLflow с **сигнатурой**: вход `image` — `float32
(N, 4, 256, 256)`, выход `probabilities` — `float32 (N, 1, 256, 256)`. Сервер отдаёт
вероятности; порог и постобработка применяются на клиенте.

### 10.2. Triton Inference Server

```bash
python commands.py prepare-triton
docker run --gpus all --rm -p 8000:8000 -p 8001:8001 -p 8002:8002 \
    -v "$PWD/triton_repo:/models" --name triton-lake \
    nvcr.io/nvidia/tritonserver:24.08-py3 tritonserver --model-repository=/models
```

`prepare-triton` создаёт `triton_repo/lake_unet/1/model.onnx` и `config.pbtxt`
(платформа `onnxruntime_onnx`, `max_batch_size: 8`, dynamic batching, вход `[4, 256, 256]`,
выход `[1, 256, 256]`). Клиентский код печатается в консоль:

```python
import numpy as np
import tritonclient.http as httpclient

client = httpclient.InferenceServerClient(url="127.0.0.1:8000")
image = np.random.rand(1, 4, 256, 256).astype(np.float32)
inp = httpclient.InferInput("image", image.shape, "FP32")
inp.set_data_from_numpy(image)
result = client.infer("lake_unet", inputs=[inp])
probabilities = result.as_numpy("probabilities")
mask = probabilities[0, 0] > 0.55
```

Когда что выбирать: MLflow Serving — проще (один процесс, модель версионируется в реестре);
Triton — если нужен батчинг нескольких запросов, несколько моделей на одном сервере и метрики
загрузки GPU.

## 11. Ограничения и как с ними жить

| Ограничение                         | Причина                                    | Что делать                                                                            |
| ----------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------- |
| Пара дат должна быть на одной сетке | иначе площади несравнимы                   | перепроецировать/обрезать заранее или задать `infer.roi`                              |
| Triton-конфиг фиксирует 256×256     | `config.pbtxt` статичен                    | для других размеров пересоберите конфиг (модель поддерживает динамические оси в ONNX) |
| Только 4 канала Sentinel-2          | модель обучена на B2/B3/B4/B8              | другие сенсоры требуют переобучения                                                   |
| Облака не маскируются на инференсе  | SCL не передаётся вместе с входным GeoTIFF | предварительно маскировать облака или брать безоблачные сцены                         |
| Сезонность                          | вода в июле и в мае различается            | сравнивать даты одного сезона или учитывать сезон в выводах                           |
| Порог из bundle                     | обучен под конкретную разметку             | при смене домена переподберите `infer.threshold` на своих данных                      |
